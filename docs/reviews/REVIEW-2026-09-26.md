## Findings

### F1 — High: zero-row populations are reported executable and can complete with no findings

**Claim contradicted.** `docs/CYCLES-DESIGN.md` says missing inputs are
`blocked`/`partial` and describes the engine as tracing every counted/listed inventory
item. Coverage tests only the presence of roles and fields; it records population size
but does not use it when choosing `executable`
(`packages/procedures-ap/src/procedures_ap/coverage.py:73-87`). The cycle executor then
accepts two empty tables as a clean run.

**Reproduction.** Run:

```powershell
.\.venv\Scripts\python.exe -c "from procedures_ap.coverage import compile_coverage; from procedures_cycles.contracts import contracts_for_scope; from procedures_cycles.engines import registered_procedures,execute_procedure; inv={'Inventory_listing':{'fields':['stock_number'],'rows':0},'Inventory_count':{'fields':['stock_number'],'rows':0}}; c=compile_coverage(inv,contracts=contracts_for_scope(['inventory']),executors=registered_procedures()); p=[x for x in c['procedures'] if x['procedure_id']=='inventory.count_listing_trace'][0]; print('coverage',p['status'],'pop',p['population'],'missing',p['missing_roles'],p['missing_fields']); print('execution',execute_procedure('inventory.count_listing_trace',{'Inventory_listing':[],'Inventory_count':[]},{}))"
```

Observed:

```text
coverage executable pop 0 missing [] {}
execution ([], {'population': 0, 'counted': 0, ... 'exceptions': 0})
```

**Impact.** A header-only or completely filtered export can be presented as an
executable procedure and then as completed without a refusal. After review/approval,
readiness can treat the selected procedure as done. A CPA could therefore lock work
that appears to have performed an inventory existence/completeness trace when no
population was tested. This is a population-completeness failure, not merely a display
problem. The same contract-level weakness should be checked across all new procedures,
especially confirmation and completion inputs.

### F2 — High: cycle scope is not enforced at execution or risk-response linkage

**Claim contradicted.** The design calls the cycle package “opt-in by scope” and says an
engagement sees cycle contracts only when the partner places the cycle in scope
(`docs/CYCLES-DESIGN.md:30-34`). `coverage()` does enforce that presentation rule, but
`run_procedure()` does not validate the requested procedure against the engagement's
scoped contracts (`service.py:481`), and `link_risk_procedures()` accepts every globally
known cycle procedure without checking scope (`service.py:831-840`).

**Reproduction.** In a fresh temporary database, create an engagement and preparer but
do not set `cycles`, then call the service directly:

```text
cycles None
coverage_has_inventory False
run {'status': 'completed', 'summary': {'population': 0, 'counted': 0, ...},
     'findings': 0, 'error': ''}
link {'risk_id': '...', 'version': 2}
risk_links ['inventory.count_listing_trace']
```

The exact command used was a `.venv\Scripts\python.exe -c` script constructing
`WorkbenchService` in `tempfile.mkdtemp()`, calling
`run_procedure(..., procedure_id='inventory.count_listing_trace')`, then assessing an
existence risk and linking the same procedure. No repository data was used.

**Impact.** A direct API caller can create a completed cycle run in an AP-only
engagement. More importantly, a high/significant risk can cite an out-of-scope cycle
procedure as its response even though coverage/readiness does not select or require
that procedure to run. The risk-response gate can therefore be satisfied by a link
that the engagement's own scope omits. The packet includes all recorded runs, so the
result is also internally inconsistent: coverage can say AP-only while run evidence
contains cycle work.

### F3 — High: one inspected line marks an entire selected multi-line disbursement inspected

**Claim contradicted.** The unrecorded-liabilities procedure selects at check level and
states that selected disbursements not yet inspected become open leads. In
`payables.py`, however, any one matched payment line adds the check number to
`inspected_checks` (`:112`); the final completeness test only compares selected check
numbers with that set (`:171`). It never verifies that every payment/voucher line of a
selected check has an inspection record.

**Reproduction.** Execute one selected $12,000 check represented by two $6,000 payment
lines, but provide an inspection only for `900-1`:

```text
selected ['900']
inspected_checks ['900']
findings [Receipt(... key=('ap.unrecorded_liabilities_search', '900-1', 'unrecorded') ...)]
missing_900_2_flagged False
```

The check exceeded the $10,000 threshold. There was no finding for missing inspection
of `900-2`.

**Impact.** One inspected invoice can make a multi-invoice check appear fully inspected.
The omitted line can contain a pre-year-end liability and pass silently, defeating the
completeness objective of the subsequent-disbursements search. Multi-line bill-payment
checks are an ordinary accounting-export shape, so this is a likely real-client failure,
not an edge case confined to malformed data.

### F4 — Medium: a normal installation does not declare the new runtime dependency

**Claim contradicted.** `assurance_application.service` now imports
`procedures_cycles` unconditionally (`service.py:37-41`), but
`packages/assurance-application/pyproject.toml` still declares only
`procedures-ap` among its procedure dependencies (`:10-15`). The README editable-install
command also omits `packages/procedures-cycles` (`README.md:75`). Pytest does not catch
this because `conftest.py` inserts every workspace package's `src` directory.

**Reproduction.** Metadata from the review environment:

```text
Name: assurance-application
Requires: assurance-artifacts, assurance-domain, assurance-persistence, procedures-ap

Name: procedures-cycles
Editable project location: ...\packages\procedures-cycles
Required-by:
```

The local import succeeds only because `procedures-cycles` happens to be separately
installed editable; it is neither required by `assurance-application` nor by the
documented install command.

**Impact.** A fresh documented deployment or a wheel installation can fail at process
startup with `ModuleNotFoundError: procedures_cycles`, including for an AP-only user,
because the import is unconditional. The passing suite is not evidence that packaging
is complete.

### F5 — Medium: QuickBooks A/R detail grain is collapsed to one arbitrary row per customer

**Claim contradicted/rollout gap.** The rollout correctly admits that QuickBooks aging
exports need adapters, but §3 describes the A/R change primarily as supporting five or
arbitrary aging buckets. Confirmation evaluation also needs an explicit grain change.
`_confirmation_rows()` builds a dictionary keyed only by customer number
(`receivables.py:110`), so multiple invoice/detail rows for one customer overwrite one
another.

**Reproduction.** Supply two A/R rows for customer C1 ($60 and $40) and one $100
customer confirmation:

```text
population 2 confirmations 1 stratum_value 100.00 sample_value 100
[(('ar.confirmations_nonstatistical', 'book_value_mismatch', 'c1'), 'CLASH',
  'customer c1: confirmation shows book value 100, the listing 40.00'),
 (('ar.confirmations_nonstatistical', 'evaluation'), 'AGREE', ...)]
```

**Impact.** A normal customer-detail export produces a false $60 mismatch because the
join compares the confirmation to the last invoice row, while projection statistics
still use the full listing. Difference estimation likewise treats invoice-row count as
the population but customer confirmations as sample items. An adapter must aggregate
to customer balance (or the engine must define and enforce a consistent sampling unit)
before these evaluations are reliable.

## Overall verdict

The cycle work is suitable today as unpushed experimental engine code for invented,
textbook-shaped fixtures and supervised methodology development. The documentation is
appropriately cautious about provenance and QuickBooks readiness, migration 8 passed
its preservation test, and the new non-SAD lock blocker works on its tested path. It
must not yet be shipped for learner reliance or used as audit evidence on a real
engagement: empty populations can pass cleanly, cycle scope can be bypassed, the
unrecorded-liabilities completeness test misses partially inspected multi-line checks,
ordinary A/R detail grain is mishandled, and a fresh installation does not acquire the
new runtime package. These findings should be resolved or explicitly gated before any
push; then the independently written QuickBooks-shaped second case should be run against
the unchanged engine to expose the remaining adapter and grain assumptions.

## Engineering follow-up (added after the independent review)

The five findings above were addressed locally on 2026-09-26 without rewriting the
original findings or verdict:

- F1: coverage now treats zero-row roles as missing, and cycle executors independently
  return explicit refusal findings for empty roles.
- F2: direct cycle execution, risk-response links, candidate suggestions, and scope
  removal now enforce the engagement's partner-approved cycle scope.
- F3: every payment line on a selected disbursement must have an inspection result;
  one line no longer marks the whole check inspected.
- F4: `assurance-application` and the documented install command now include
  `procedures-cycles`; refreshed package metadata and `pip check` confirm the dependency.
- F5: A/R summary and detail rows are aggregated to customer balance before all three
  confirmation evaluation methods determine population and projection values.

Regression tests were added for F1, F2, F3, and F5. The full suite reports
`260 passed in 21.41s`; focused cycle tests report `28 passed in 0.61s`; `pip check`
reports `No broken requirements found`. This is an engineering status note, not an
independent re-review. The changes remain uncommitted and unpushed.
