# Independent review — Noesi Assurance Workbench

- **Date:** 2026-08-07
- **Reviewer:** Independent AI session (did not build this software)
- **Commit reviewed:** `f3bb523` (branch `main`), working tree clean
- **Method:** `docs/INDEPENDENT-REVIEW.md`. Full pytest suite plus direct
  attacks on the seven designed invariants. Separation-of-duties and the API
  boundary were driven against the live HTTP server with `X-Acting-Principal`,
  never through the UI. Lock/packet integrity was checked with an
  **independent** verifier (raw `cryptography` primitives), not the repo's
  own `verify_packet`.

  `>=3.12`. The suite and all attacks nonetheless passed; no 3.12-only
  behavior was observed, but the version floor was not exercised.

Checked, by running commands and reading output:

- Full test suite (`python -m pytest tests -q`).
- **Invariant 1 — coverage honesty:** executor-registry reconciliation and
  partial-data behavior, in-process against `compile_coverage`.
- **Invariant 2 — reperformance/digest:** vault-blob and recorded-digest

  path, driven over HTTP with a single identity deliberately holding multiple

- **Invariant 4 — the lock as evidence:** partner-only lock, signed snapshot,

  **offline packet verification with an independent crypto script**.
- **Invariant 5 — hardened boundary:** auth on reads, Host/Origin checks,

  traversal, security headers.
- **Invariant 6 — teaching-case honesty:** reconciliation of engine findings
  against `instructor/ANSWER-KEY.md`, including the deliberately-silent item.
- **Invariant 7 — license/provenance:** header scan across all source files,
  LICENSE, README disclaimers, PROVENANCE presence.

**Not** checked (see the dedicated section): the React UI, KOMPOSOS upstream
provenance, trusted-time / key-custody / encryption-at-rest (admitted P0/P1

## Findings

No finding contradicts a core invariant. Every invariant held under direct
attack (see Confirmations). The items below are lower-severity defects and
one already-admitted gap I was able to reproduce.

### F1 — Low. Invalid disposition status is reported as a bogus "version conflict"

**Claim touched:** none directly; this is an error-reporting defect adjacent
to Invariant 3.

`WorkbenchService.set_disposition` passes `status` straight to the INSERT
without validating it against the allowed set. The `disposition` table has
`CHECK (status IN ('cleared','unadjusted','adjusted','waived','follow_up'))`.
An out-of-set status therefore raises `sqlite3.IntegrityError`, which
`DispositionRepository.set` (spine.py:260) catches and unconditionally
re-labels as `ConflictError(..., 0)` — an optimistic-concurrency message.

**Reproduction (HTTP):**

```
POST /api/engagements/<eid>/dispositions
  body: {"finding_uid":"x|1","status":"accepted_as_is","expected_version":0}
-> 409 {"error":"disposition <eid>/x|1 is no longer at version 0"}
```

The disposition table was confirmed empty at the time, so no version conflict
existed. The real cause is the rejected status value.

**Impact (audit practice):** a preparer/reviewer who types a status the API
does not accept is told the record "is no longer at version 0" — implying a
concurrent edit that did not happen. Cosmetic and fail-safe (no bad data is
written), but misleading during a disposition workflow. Fix is a status
allow-list check before the write, returning a 400 that names the field.

### F2 — Low. `verify_run.py` reconciliation aid omits the key for the composite procedure

**Claim touched:** Invariant 6 ("`verify_run.py` reproduces what the engine
finds … so they can be reconciled line by line against `ANSWER-KEY.md`").

`verify_run.py` prints only `verdict['reason']`. For ten of eleven procedures
the reason contains the reference id, so line-matching works. For the
composite `ap.document_chain` the reasons are aggregate strings
("payment/voucher amount difference 18.0%", "dates do not follow PO -> voucher
-> payment order") with **no id**. Its 15 findings cannot be matched to the 5
planted `document_chain` rows from stdout alone.

**Verification that this is a *print* limitation, not a false negative:**
querying the engine directly, every `document_chain` finding carries the id in
`verdict['key']` — all five planted references are present:

```
['document_chain', 'PAY-2026-0016']  payment/voucher amount difference 18.0%
['document_chain', 'PAY-2026-0018']  dates do not follow PO -> voucher -> payment order
['document_chain', 'PAY-2026-0093']  payment/voucher amount difference 18.0%
['document_chain', 'PAY-2026-0085']  dates do not follow PO -> voucher -> payment order
['document_chain', 'PAY-2026-0109']  payment/voucher amount difference 18.0%
```

**Impact:** an instructor trusting the script's stdout to reconcile the
`document_chain` block cannot, and might read the mismatch (15 vs 5) as an
engine error. The data is honest; the aid is incomplete. Printing
`verdict['key']` alongside the reason would close it.

### F3 — Low. Digest/vault refusals surface as an opaque HTTP 500

**Claim touched:** Invariant 2 (the refusal is correct; only its *presentation*
at the boundary is weak).

When reperformance fails (vault-blob tamper → `VaultIntegrityError`;
recorded-digest tamper → `RuntimeError`), the read fails closed — good. But
neither exception is mapped in `server._handle`, so the client receives a bare
`500 {"error":"internal error"}` rather than a message naming the integrity
failure. The system does the right thing (refuses to serve unverifiable data);
it just does not *tell* the operator that integrity, not a crash, is the
cause.

**Impact:** low. Safety is preserved. A CPA seeing "internal error" on a
tampered/corrupted file would not know to suspect the evidence chain. Mapping
these to a 409/422 with an integrity message would make the refusal legible.

### C1 (context, already admitted) — the data-less lock hole is real

`docs/PRODUCTION-READINESS.md` §3.4 lists it; I reproduced it. A fresh
engagement with **zero normalized datasets** reaches `ready: true` on
workflow gates alone (materiality + two stage completions + six completion
checks) and locks with a valid signature — no procedure ever runs.

```
create engagement -> set materiality -> stages complete -> completion checks done
GET .../readiness -> {"ready": true, "blockers": []}
POST .../lock      -> {"locked": true, ...}   (no data, no procedures)
```

Cited per the brief as context, not a discovery. It remains the sharpest gap
on the list: a locked, signed engagement can attest to having done no
data-dependent work at all, with nothing in the record forcing the partner to
say so.

## Confirmations (attacked and could not break)

Commands were run against a live server on `127.0.0.1:8471` seeded with the
Harborline demo (`python -m workbench_api --data <scratch> --port 8471 --demo`)
unless noted as in-process.

**Test suite.** `python -m pytest tests -q` → **150 passed**.

**Invariant 1 — coverage honesty.** 11 contracts and 11 registered executors,
exactly aligned (no contract without an engine; no engine without a contract).
With only `Vendors` loaded, coverage reports **0 executable / 10 blocked / 1
partial**, each blocked row naming its `missing_roles`. De-registering one
executor flips that procedure to `unsupported` with the honest reason "no
executor is registered for this procedure in this build." Coverage never
claimed executable for missing data or a missing engine.

**Invariant 2 — reperformance is digest-verified.** A clean read succeeds;
appending one byte to the vault blob makes the next read raise
`VaultIntegrityError`; corrupting the recorded `output_digest` makes it raise
`RuntimeError: dataset … no longer reproduces its recorded digest; refusing to
serve unverifiable data`. Both refuse; neither serves.

**Invariant 3 — separation of duties, server-side.** Driven over HTTP with one
identity holding multiple roles so the *identity* check (not the role gate)
was the thing under test:

| Attack | Result |
|---|---|
| Proposer approves own mapping (also holds reviewer) | `409` "the preparing principal may not approve their own work" |
| Executor reviews own run (also holds reviewer) | `409` same |
| Disposition proposer concurs own (reviewer) | `409` same |
| Reviewer approves a run (needs partner) | `403` "approved requires a partner" |
| Non-partner locks a **ready** engagement | `403` "locking requires the partner" |

A distinct second principal succeeded in each positive path, so the refusals
are the separation check, not a stuck workflow.

**Invariant 4 — the lock is evidence.** Partner lock produced a signed
snapshot; `verify_lock` returned `verified: true, drift: []`. Inserting a
disposition row directly into the DB behind the lock made `verify_lock` report
`verified: false, drift: ['dispositions'], snapshot_ok: false` while
`signature_ok` stayed true (the signature still binds the original bytes), and
`export` then **refused** with `400 export refused: the lock does not verify`.
Unlock required the partner and a ≥10-char reason, superseded (did not delete)
the prior snapshot, and relock named its predecessor. The exported packet
verified under an **independent** script (recomputing `sha256(canonical json)`
and checking the ed25519 signatures with `cryptography` directly, not the
repo's verifier): packet digest reproduces, export signature valid, lock
manifest digest reproduces, lock signature valid, and the superseded lock in
`lock_history` verified the same way. Changing one field of the packet broke
the digest reproduction, as it must.

**Invariant 5 — hardened boundary.**

| Attack | Result |
|---|---|
| Unauthenticated `GET /api/engagements` | `401` |
| Wrong bearer token | `401` |
| Forged `Host: evil.com` | `403` |
| Forged `Origin: http://evil.com` | `403` |
| Correct loopback Origin | `200` |
| Path traversal `--path-as-is /../../../conftest.py` (and encoded/nested variants) | `404 "unknown path"`, no file bytes returned |
| Oversize JSON body (>2 MB) | `413` |
| `POST` with no `Content-Length` | `411` |
| `X-Acting-Principal` containing whitespace | `400` |

Security headers (`Content-Security-Policy: default-src 'none'`, nosniff,
frame DENY, no-referrer, no-store) present on API responses; the static shell
is served tokenless but Host-checked with a scripts-`self` CSP, and the
session token is injected only into that loopback-served `index.html`.

**Invariant 6 — teaching-case honesty.** `verify_run.py` runs all 11
procedures (all `executable`, all complete without error) and emits 52 raw
findings. Reconciled against `ANSWER-KEY.md` (40 planted): **all 40 planted
references are found** (the 5 `document_chain` items confirmed via
`verdict['key']`, per F2). The one deliberately-silent planted item —
`PAY-2026-0025`, a bank clearing 0.9 % inside the engine's 2 % tolerance —
is **correctly not reported** (`0` occurrences in output). The excess over 40
is composite/cross-procedure overlap that `ANSWER-KEY.md` explicitly
anticipates; the tool reports what it finds and makes no recall claim.

**Invariant 7 — license and provenance.** All **75** `.py`/`.ts`/`.tsx`
source files under `packages/`, `apps/`, `case-studies/`, `tests/` carry the
identical header `Copyright (c) 2026 James Hawkins. PolyForm Noncommercial
License 1.0.0 — see LICENSE.md.` `LICENSE.md` is PolyForm Noncommercial 1.0.0
with James Hawkins named; `README.md` carries the "not an audit / not
professional advice / noncommercial" disclaimers; `docs/PROVENANCE.md` exists
and documents the KOMPOSOS-derived `structural-adapters`.

## Not checked

- **KOMPOSOS upstream provenance.** `docs/PROVENANCE.md` marks its ownership
  claims `[V]` against local source checkouts not present in this repo. I
  confirmed the document exists and that headers/LICENSE are internally
  consistent, but did **not** independently verify the upstream license of the
  ported `structural-adapters` code.
- **The React UI.** Per the brief I drove the HTTP API directly. The built
  `dist/` is served and is path-traversal-safe, but no UI behavior was tested.
- **A full data-backed lock.** I confirmed every readiness gate and the lock
  machinery individually, and drove the complete lock/supersession/packet
  cycle on the data-less path (C1). I did not orchestrate all 40 Harborline
  exceptions through run → review → approve → disposition → concurrence to a
  data-backed lock; the lock/packet machinery is identical regardless.
- **Admitted P0/P1 platform gaps** (trusted time, key custody, encryption at
  rest, retention/WORM, concurrency, scale). Out of scope for behavioral
  attack; they are correctly disclosed in `PRODUCTION-READINESS.md` and stated
  in-band in the packet/manifest limits. They bound what the tool may be
  relied on for (below).
- **Python version floor.** Ran on 3.10.11, not the stated ≥3.12.

## Overall verdict

This build does what it claims about **evidence integrity and honesty**, and I
could not break any of the seven invariants. Coverage never overclaimed;
reads reperform from immutable artifacts and refuse when a digest fails;
separation of duties is enforced in the domain by principal identity, not the
UI, and survives a single operator wearing every hat; the lock is a real
signed, journal-anchored manifest whose drift is named and whose packet
verifies offline under an independent verifier; the API boundary refused every
malformed and unauthorized request I sent; and the teaching case is honest,
down to the one planted difference designed to stay silent. Licensing and
headers are consistent. The three defects found are low-severity and
fail-safe (a misleading error message, an incomplete reconciliation printout,
and an opaque-but-correct 500 on tampered evidence).

**May be used today** as: a teaching and research instrument; a
reproducible AP-procedure coverage-and-evidence workbench where the value is
the *discipline* — honest capability reporting, digest-verified
reperformance, enforced separation of duties, and a tamper-evident,
independently-verifiable evidence packet.

**Must not be used yet** as: a system of record for a real client engagement
or the basis of an issued opinion. The blockers are the builder's own admitted
P0 gaps, not defects I found — no per-person authentication (chairs are
role-play over one token), no trusted time, no key custody beyond a local
unencrypted PEM, no encryption at rest, no immutable retention — **plus** the
data-less lock hole (C1): until readiness forces an explicit partner assertion
when no data-dependent procedure ran, a signed lock can silently attest to no
substantive work. Treat every signature as proving *only* what its in-band
limits say — which principal's local key approved which bytes, and when by an
untrusted clock — and nothing about the authenticity or completeness of the
underlying accounting records.
